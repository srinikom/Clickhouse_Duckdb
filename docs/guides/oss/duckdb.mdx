ClickHouse can use [DuckDB](https://duckdb.org) as an embedded database for OLTP-style tables: tables with transactional inserts, stored in a single DuckDB file next to the server. This page describes how to build and configure the integration, how to use it, and how to test it by hand.

<Note>
The integration is Linux only and is disabled in a default build. It talks to DuckDB through the DuckDB C API and links the prebuilt `libduckdb.so`, so the library is a run-time dependency of the `clickhouse` binary.
</Note>

## What is included {#what-is-included}

| Part | Purpose |
| --- | --- |
| `DuckDB` table engine | A ClickHouse table backed by a table of a DuckDB file. Supports `SELECT` and transactional `INSERT`. |
| `duckdb` table function | Runs a DuckDB query and returns its result. It makes the functions of DuckDB extensions, such as `read_parquet`, available. Read-only. |
| `duckdbVersion` | The version of the DuckDB library. |
| `duckdbExtensions` | Lists the extensions of DuckDB with their state. |
| `duckdbExtensionFunctions` | Maps the loaded extensions to the functions they provide. |
| `duckdbInstallExtension`, `duckdbLoadExtension` | Install and load an extension. |
| `duckdb` section of the server configuration | Turns on and controls extensions and the table function. |

## Build and run {#build-and-run}

1. Download the `libduckdb-linux-*.zip` archive of a [DuckDB release](https://github.com/duckdb/duckdb/releases) and unpack it. It contains `duckdb.h` and `libduckdb.so`.
2. Configure ClickHouse with `ENABLE_DUCKDB` and point `DUCKDB_ROOT` to the directory:

```bash
DUCKDB_ROOT=/path/to/unpacked/zip cmake -DENABLE_DUCKDB=1 ..
ninja clickhouse
```

3. Make the library visible at run time, next to the binary or through `LD_LIBRARY_PATH`:

```bash
export LD_LIBRARY_PATH=/path/to/unpacked/zip
./clickhouse server
```

Check that the build contains the integration:

```sql
SELECT value FROM system.build_options WHERE name = 'USE_DUCKDB';
SELECT duckdbVersion();
```

## Server configuration {#server-configuration}

Everything that reaches outside the DuckDB file is controlled by the `duckdb` section of the server configuration. It is not a query setting on purpose: it is security sensitive, so only the administrator can change it. The values are read when a DuckDB database is opened, so a change applies to the databases opened afterwards. Restart the server, or drop and create the tables again, to apply it to the open ones.

The section can be written in XML or in YAML, in `config.xml` / `config.yaml` or in a file of `config.d`. Both forms mean the same:

<Tabs>
  <Tab title="XML">

```xml
<clickhouse>
    <duckdb>
        <allow_extensions>1</allow_extensions>
        <allowed_extensions>json, parquet, inet</allowed_extensions>
        <preload_extensions>json</preload_extensions>
        <extension_directory>/var/lib/clickhouse/duckdb_extensions/</extension_directory>
        <allow_extension_loading>1</allow_extension_loading>
        <allow_unsigned_extensions>0</allow_unsigned_extensions>
        <allow_community_extensions>0</allow_community_extensions>
        <allow_extension_files>0</allow_extension_files>
        <custom_extension_repository></custom_extension_repository>
        <allow_arbitrary_sql>1</allow_arbitrary_sql>
    </duckdb>
</clickhouse>
```

  </Tab>
  <Tab title="YAML">

```yaml
duckdb:
    allow_extensions: 1
    allowed_extensions: json, parquet, inet
    preload_extensions: json
    extension_directory: /var/lib/clickhouse/duckdb_extensions/
    allow_extension_loading: 1
    allow_unsigned_extensions: 0
    allow_community_extensions: 0
    allow_extension_files: 0
    custom_extension_repository: ''
    allow_arbitrary_sql: 1
```

  </Tab>
</Tabs>

| Key | Default | Meaning |
| --- | --- | --- |
| `allow_extensions` | `0` | The main switch. It enables the extension functions, and DuckDB is opened with external access, which installing an extension and reading files need. When off, DuckDB is opened without access to the file system and the network, nothing is installed or loaded implicitly, and all the keys below are ignored. |
| `allowed_extensions` | empty | Comma-separated names of the extensions that can be installed or loaded. `*` allows any extension. Nothing is allowed by default. A name has to consist of letters, digits and `_`. |
| `preload_extensions` | empty | Names loaded whenever a database is opened. They must be allowed by `allowed_extensions`. |
| `extension_directory` | `duckdb_extensions` in the server data directory | Where extensions are installed. |
| `allow_extension_loading` | `0` | Allows loading the extensions that are not built into `libduckdb.so`. They are native code, and loading one needs `dlopen`, which is forbidden in the `clickhouse` binary. With this key it is allowed only for the time of loading an extension. While a load runs, `dlopen` is open for the whole process, not only for that call, so loads are serialized, and nothing else in the server calls `dlopen`. |
| `allow_unsigned_extensions` | `0` | Allows extensions that are not signed by DuckDB, such as your own build. |
| `allow_community_extensions` | `0` | Allows installing from the DuckDB community repository, `duckdbInstallExtension('name', 'community')`. |
| `allow_extension_files` | `0` | Allows an extension file of `user_files` as the extension in `duckdbInstallExtension` and `duckdbLoadExtension`. |
| `custom_extension_repository` | empty | The repository that `INSTALL` downloads extensions from, instead of the official one. |
| `allow_arbitrary_sql` | `0` | Enables the `duckdb` table function. |

<Warning>
`allowed_extensions` = `*` together with `allow_extension_loading` and `allow_unsigned_extensions` lets any user who holds the `WRITE` grant on the `FILE` source run native code of an arbitrary library inside the server process. Allow only what you need, list the extensions by name, and prefer the official signed extensions.
</Warning>

You can take a value from the environment with `from_env` in XML, which is useful in containers:

```xml
<clickhouse>
    <duckdb>
        <allow_extensions from_env="DUCKDB_ALLOW_EXTENSIONS"/>
        <allowed_extensions>json, parquet</allowed_extensions>
    </duckdb>
</clickhouse>
```

`from_env` is an XML feature. With YAML, generate the file for the environment instead.

Put the file into `config.d`. The server rejects unknown top-level sections, so the `duckdb` section requires a build that contains the integration.

## The `DuckDB` table engine {#duckdb-table-engine}

```sql
CREATE TABLE t (id Int32, name String, created DateTime)
ENGINE = DuckDB('app.duckdb', 't');
```

The first argument is a path inside `user_files`, the second is the name of the table in DuckDB.

- With an explicit column list, `CREATE` creates the DuckDB table (and the file) if it does not exist. The columns that are not `Nullable` become `NOT NULL`.
- Without a column list, the structure is inferred from an existing DuckDB table. Every inferred column is `Nullable`.
- `ATTACH`, for example when the server starts, never writes to the database.
- A DuckDB file can be opened by one process only, so the `duckdb` command line cannot use the file while the server holds it.

### Transactions {#transactions}

Every `INSERT` runs in one DuckDB transaction:

- its rows are invisible to other queries until it commits;
- if it fails or is cancelled (`KILL QUERY`), everything it wrote is rolled back;
- two inserts into the same table can run at the same time, and each commits independently. A failing insert does not affect the other.

There are no multi-statement transactions controlled by the user.

## The `duckdb` table function {#duckdb-table-function}

```sql
duckdb('database_path', 'query')
```

It runs a DuckDB `SELECT` and returns its result, so the functions of the extensions can be used:

```sql
SELECT * FROM duckdb('', 'SELECT * FROM read_parquet(''/var/lib/clickhouse/user_files/data.parquet'')');
SELECT * FROM duckdb('app.duckdb', 'SELECT id, count(*) AS n FROM t GROUP BY id');
```

- `database_path` is a file inside `user_files`, or an empty string for a private in-memory database.
- The query is passed to DuckDB as is. Quote a single quote inside it by doubling it. It must be a single statement without a semicolon at the end.
- The result is read-only and its columns are `Nullable`. A DuckDB type that ClickHouse cannot represent, such as `MAP`, is rejected with `NOT_IMPLEMENTED`; select the columns you need instead of `*`.
- It needs `duckdb.allow_arbitrary_sql` and the `READ` grant on the `FILE` source.

<Warning>
The query can do everything DuckDB can do with external access, including reading any file the server can read. Enable `allow_arbitrary_sql` only if the users who hold the `READ` grant on the `FILE` source are trusted.
</Warning>

The structure of the result is found by preparing the query, which does not run it, and DuckDB refuses to prepare several statements. A query that tries to append a second statement fails with `DUCKDB_ENGINE_ERROR` before anything is executed.

## Extensions {#extensions}

### Functions {#functions}

All of them, except `duckdbVersion`, need `duckdb.allow_extensions` and the `WRITE` grant on the `FILE` source. Without the setting they fail with `SUPPORT_IS_DISABLED`.

```sql
SELECT duckdbVersion();

-- all extensions known to DuckDB, installed and loaded state
SELECT arrayJoin(duckdbExtensions()) AS e;
-- the same for a database file
SELECT arrayJoin(duckdbExtensions('app.duckdb')) AS e;

-- the functions of the loaded extensions
SELECT arrayJoin(duckdbExtensionFunctions('app.duckdb')) AS f WHERE f.extension = 'inet';

SELECT duckdbInstallExtension('inet');                       -- the official repository
SELECT duckdbInstallExtension('nanoarrow', 'community');     -- the community repository
SELECT duckdbInstallExtension('ext/my.duckdb_extension');    -- a file of user_files
SELECT duckdbLoadExtension('app.duckdb', 'inet');
SELECT duckdbLoadExtension('app.duckdb', 'ext/my.duckdb_extension');
```

`duckdbExtensions` returns `Array(Tuple(name, installed, loaded, version, description))`. `duckdbExtensionFunctions` returns `Array(Tuple(extension, name, type))`, for example `('inet', 'host', 'scalar')`.

### How an extension is loaded {#how-an-extension-is-loaded}

1. The extension has to be allowed: its name is in `allowed_extensions` (or the list is `*`), or it is a file and `allow_extension_files` is set. A file is read from `user_files` only.
2. The extensions linked into `libduckdb.so` (`json`, `parquet`, `icu`, `core_functions`, `autocomplete`) are loaded from the start. They need no installation and no `dlopen`.
3. Any other extension is installed into `extension_directory` (`duckdbInstallExtension`, or copy the file there) and loaded into a database (`duckdbLoadExtension`, or `preload_extensions`). Loading needs `allow_extension_loading`, because it is native code. Without it the call fails with `SUPPORT_IS_DISABLED` before anything is loaded.
4. An extension that is not signed by DuckDB is rejected by DuckDB unless `allow_unsigned_extensions` is set.

A loaded extension stays loaded while a `DuckDB` table keeps the database open. Use `preload_extensions` to load an extension in every database.

### The map of the functions {#the-map-of-the-functions}

DuckDB does not say which extension a function belongs to, so `duckdbExtensionFunctions` registers them in two ways:

- When an extension is loaded, the functions of the database are compared before and after the `LOAD`, and the new ones are recorded for that extension. This covers every extension that is loaded after the start, including your own.
- The extensions built into the library are loaded before there is anything to compare, so `parquet`, `json`, `icu` and `autocomplete` have a fixed list of function names, filtered to the functions the database actually has.

An extension may add things that are not functions, such as file systems (`httpfs`) or settings, and then its list is empty.

## Example: ingest into DuckDB and copy to MergeTree {#example-ingest-and-copy}

This example uses the `DuckDB` engine as the write side (OLTP) and a native `MergeTree` table as the analytics side. Each insert into the DuckDB table is copied into the `MergeTree` table by a materialized view. The paths assume a server started as in [Manual testing](#manual-testing), with `/tmp/ch/user_files` as the `user_files` directory.

### 1. Create the tables and the views {#example-create}

```sql
-- Start clean
DROP TABLE IF EXISTS orders_to_mt;
DROP TABLE IF EXISTS orders_daily_mv;
DROP TABLE IF EXISTS orders_daily;
DROP TABLE IF EXISTS orders_mt;
DROP TABLE IF EXISTS orders_oltp;

-- OLTP side: the table lives in the DuckDB file
CREATE TABLE orders_oltp
(
    order_id Int64,
    customer String,
    amount Decimal(10, 2),
    status String,
    created_at DateTime64(3, 'UTC')
)
ENGINE = DuckDB('/tmp/ch/user_files/shop.duckdb', 'orders');

-- Analytics side: native MergeTree
CREATE TABLE orders_mt
(
    order_id Int64,
    customer String,
    amount Decimal(10, 2),
    status String,
    created_at DateTime64(3, 'UTC')
)
ENGINE = MergeTree ORDER BY (created_at, order_id);

-- Copy what is already in DuckDB, then attach the live feed
INSERT INTO orders_mt SELECT * FROM orders_oltp;
CREATE MATERIALIZED VIEW orders_to_mt TO orders_mt AS SELECT * FROM orders_oltp;

-- Optional: a daily rollup, fed from the MergeTree table
CREATE TABLE orders_daily
(
    day Date,
    orders AggregateFunction(count),
    revenue AggregateFunction(sum, Decimal(10, 2))
)
ENGINE = AggregatingMergeTree ORDER BY day;

CREATE MATERIALIZED VIEW orders_daily_mv TO orders_daily AS
SELECT toDate(created_at) AS day, countState() AS orders, sumState(amount) AS revenue
FROM orders_mt GROUP BY day;
```

Copy the rows that already exist before you create the view, as above. The view copies only the rows inserted after it exists, so creating it first and copying afterwards can insert the same rows twice.

### 2. Ingest into DuckDB {#example-ingest}

```sql
INSERT INTO orders_oltp VALUES
    (1, 'alice', 10.50, 'new',  '2026-10-01 10:00:00.000'),
    (2, 'bob',   20.00, 'new',  '2026-10-01 11:30:00.000'),
    (3, 'alice',  5.25, 'paid', '2026-10-02 09:15:00.000');
INSERT INTO orders_oltp VALUES (4, 'carol', 99.99, 'new', '2026-10-02 12:00:00.000');
```

### 3. Check both sides {#example-check}

```sql
SELECT 'duckdb', count(), sum(amount) FROM orders_oltp;
SELECT 'mergetree', count(), sum(amount) FROM orders_mt;

SELECT day, countMerge(orders) AS orders, sumMerge(revenue) AS revenue
FROM orders_daily GROUP BY day ORDER BY day;

SELECT customer, count() AS orders, sum(amount) AS total
FROM orders_mt GROUP BY customer ORDER BY total DESC;
```

The output:

```text
duckdb     4  135.74
mergetree  4  135.74
2026-10-01  2   30.5
2026-10-02  2  105.24
carol 1 99.99
bob   1 20
alice 2 15.75
```

Both tables hold the same rows. The DuckDB table stays the source of truth, and the analytics queries run on the `MergeTree` table.

### 4. Catch up on missed rows {#example-catch-up}

The view fires only on inserts made through ClickHouse. Rows that another process wrote into `shop.duckdb`, and rows inserted while the view did not exist, are not copied. This query copies the rows after the highest `order_id` that `orders_mt` already holds. It needs `duckdb.allow_arbitrary_sql`:

```sql
INSERT INTO orders_mt
SELECT * FROM duckdb('/tmp/ch/user_files/shop.duckdb', 'SELECT * FROM orders')
WHERE order_id > (SELECT max(order_id) FROM orders_mt);
```

It added no duplicates when nothing was missing. It was not tested against a real external writer, because the `duckdb` table function is read-only. Without `allow_arbitrary_sql`, use `INSERT INTO orders_mt SELECT * FROM orders_oltp WHERE order_id > ...`.

### 5. Choose how to copy {#example-choose}

| Approach | Copies | Use it for |
| --- | --- | --- |
| `INSERT INTO mt SELECT * FROM duckdb_table` | The rows now, once | Existing data. Add a `WHERE` on an id or a timestamp to copy in batches. |
| `CREATE MATERIALIZED VIEW ... TO mt AS SELECT * FROM duckdb_table` | Each later insert made through ClickHouse | Live ingestion through ClickHouse. |
| `CREATE MATERIALIZED VIEW ... REFRESH EVERY 1 MINUTE ENGINE = MergeTree ... AS SELECT * FROM duckdb_table` | The whole table on each refresh, including rows written outside ClickHouse | Small tables, or rows written by other processes. It needs `allow_experimental_refreshable_materialized_view = 1`. |

### 6. Limits of this pattern {#example-limits}

- The engine does not support `UPDATE` or `DELETE`, and the view copies only inserts. For status changes, insert a new row for each change and use `ReplacingMergeTree(updated_at)` for `orders_mt`.
- If the insert into DuckDB succeeds but the copy into `orders_mt` fails, the row stays in DuckDB. Use the catch-up query to repair it.
- `WHERE` outside the `duckdb` call is not pushed into DuckDB, so the catch-up query reads the whole table. For a big table, filter in the inner query, for example `'SELECT * FROM orders WHERE order_id > 1000000'`.

## Manual testing {#manual-testing}

The commands below start from a built `clickhouse` binary and `libduckdb.so`. Replace the paths. All the SQL can be run in `clickhouse client`.

### 1. Start a server {#start-a-server}

```bash
mkdir -p /tmp/ch/{data,user_files,tmp,config.d}
cp programs/server/config.xml programs/server/users.xml /tmp/ch/

cat > /tmp/ch/config.d/duckdb.xml <<'XML'
<clickhouse>
    <duckdb>
        <allow_extensions>1</allow_extensions>
        <allowed_extensions>*</allowed_extensions>
        <preload_extensions>json,parquet</preload_extensions>
        <extension_directory>/tmp/ch/duckdb_extensions/</extension_directory>
        <allow_arbitrary_sql>1</allow_arbitrary_sql>
        <allow_extension_loading>1</allow_extension_loading>
        <allow_extension_files>1</allow_extension_files>
        <allow_community_extensions>1</allow_community_extensions>
        <allow_unsigned_extensions>1</allow_unsigned_extensions>
    </duckdb>
</clickhouse>
XML

cd /tmp/ch
LD_LIBRARY_PATH=/path/to/libduckdb ./clickhouse server -- \
    --path=/tmp/ch/data/ --user_files_path=/tmp/ch/user_files/ --tmp_path=/tmp/ch/tmp/
```

The same settings in YAML, `/tmp/ch/config.d/duckdb.yaml` instead of the XML file:

```yaml
duckdb:
    allow_extensions: 1
    allowed_extensions: "*"
    preload_extensions: json,parquet
    extension_directory: /tmp/ch/duckdb_extensions/
    allow_arbitrary_sql: 1
    allow_extension_loading: 1
    allow_extension_files: 1
    allow_community_extensions: 1
    allow_unsigned_extensions: 1
```

Quote the `*` in YAML. The server reads `config.xml` and `config.d` from the current directory. The `--path` directory has to exist and end with a slash. In a Docker container, run the same commands inside it and set `LD_LIBRARY_PATH` in the container environment.

### 2. Check the build and the settings {#check-the-build-and-the-settings}

```sql
SELECT duckdbVersion();
SELECT arrayJoin(duckdbExtensions()) AS e WHERE e.loaded;
```

Expected: the version, for example `v1.5.6`, and the built-in extensions `autocomplete`, `core_functions`, `icu`, `json`, `parquet` as loaded. With `allow_extensions` off the second query fails with `SUPPORT_IS_DISABLED`.

### 3. The table engine and transactions {#test-the-table-engine}

```sql
CREATE TABLE t (id Int32, name String) ENGINE = DuckDB('app.duckdb', 't');
INSERT INTO t VALUES (1, 'a'), (2, 'b'), (3, 'c');
SELECT * FROM t ORDER BY id;

-- the structure is inferred from the existing table
CREATE TABLE t2 ENGINE = DuckDB('app.duckdb', 't');
SHOW CREATE TABLE t2;

-- a path outside user_files is rejected
CREATE TABLE bad (x Int32) ENGINE = DuckDB('/etc/x.duckdb', 'x');  -- PATH_ACCESS_DENIED
```

To see that an insert is invisible until it commits, run a slow insert in one `clickhouse client` session and count the rows in another:

```sql
-- session 1: 30 rows, 50 ms per row
INSERT INTO t SELECT number + 100, 'slow' FROM numbers(30) WHERE sleepEachRow(0.05) = 0
SETTINGS max_block_size = 1, max_threads = 1;

-- session 2, while it runs
SELECT count() FROM t WHERE name = 'slow';   -- 0
-- after it finishes
SELECT count() FROM t WHERE name = 'slow';   -- 30
```

Run the insert again, and while it runs find and cancel it in session 2:

```sql
SELECT query_id FROM system.processes WHERE query LIKE 'INSERT INTO t%';
KILL QUERY WHERE query_id = '<query_id>' SYNC;
SELECT count() FROM t WHERE name = 'slow';   -- unchanged: the insert was rolled back
```

Two writers: start the slow insert in two sessions with different ids at the same time. Both commit, and the table gets the rows of both.

### 4. The table function and the Parquet extension {#test-the-parquet-extension}

ClickHouse can be built without the Parquet format, so create a Parquet file with DuckDB itself, for example with the Python package (`python3 -m pip install duckdb`):

```bash
python3 -c "import duckdb; duckdb.sql(\"COPY (SELECT range AS id, CAST(range AS VARCHAR) AS name, range * 1.5 AS score FROM range(5)) TO '/tmp/ch/user_files/data.parquet' (FORMAT parquet)\")"
```

```sql
SELECT * FROM duckdb('', 'SELECT * FROM read_parquet(''/tmp/ch/user_files/data.parquet'')') ORDER BY id;
SELECT sum(score) FROM duckdb('', 'SELECT * FROM read_parquet(''/tmp/ch/user_files/data.parquet'')');   -- 15
SELECT * FROM duckdb('', 'SELECT 42 AS answer');
SELECT * FROM duckdb('app.duckdb', 'SELECT id, upper(name) AS n FROM t WHERE id > 1');
```

The functions of an extension are only known to DuckDB, so calling one directly in ClickHouse fails:

```sql
SELECT * FROM read_parquet('/tmp/ch/user_files/data.parquet');   -- UNKNOWN_FUNCTION
```

### 5. The extension map {#test-the-extension-map}

```sql
SELECT arrayJoin(duckdbExtensionFunctions()) AS f
WHERE f.name IN ('read_parquet', 'read_json', 'json_extract')
ORDER BY f.name;
```

Expected:

```text
('json','json_extract','scalar')
('json','read_json','table')
('parquet','read_parquet','table')
```

### 6. Install and load an external extension {#test-install-and-load}

Use a configuration with `allowed_extensions` = `*`, `allow_extension_loading`, `allow_extension_files`, `allow_community_extensions` and `allow_unsigned_extensions` set to `1`. `duckdbInstallExtension` downloads the extension, so the server needs network access. `inet` is not built into the library, so loading it goes through the dynamic loader:

```sql
SELECT count() FROM t;                                                -- a table keeps the database open
SELECT duckdbInstallExtension('inet');                                -- 1
SELECT arrayFilter(e -> e.name = 'inet', duckdbExtensions('app.duckdb'));   -- installed = 1, loaded = 0
SELECT duckdbLoadExtension('app.duckdb', 'inet');                     -- 1
SELECT arrayFilter(e -> e.name = 'inet', duckdbExtensions('app.duckdb'));   -- loaded = 1
SELECT arrayJoin(duckdbExtensionFunctions('app.duckdb')) AS f
WHERE f.extension = 'inet' ORDER BY f.name LIMIT 3;
-- ('inet','<<=','scalar')  ('inet','>>=','scalar')  ('inet','broadcast','scalar')
SELECT * FROM duckdb('app.duckdb', 'SELECT host(''192.168.1.5/24''::INET)::VARCHAR AS h, family(''::1''::INET) AS fam');
-- 192.168.1.5   6
```

The community repository and the repository check:

```sql
SELECT duckdbInstallExtension('nanoarrow', 'community');   -- 1 with allow_community_extensions, otherwise SUPPORT_IS_DISABLED
SELECT duckdbInstallExtension('x', 'evil');                -- BAD_ARGUMENTS: unknown repository
SELECT duckdbInstallExtension('no_such_extension_xyz');    -- DUCKDB_ENGINE_ERROR: HTTP 404
```

Load an extension from a file of `user_files`. Copy the installed `inet` file there and load it into a database where it is not loaded yet:

```bash
mkdir -p /tmp/ch/user_files/ext
cp /tmp/ch/duckdb_extensions/v*/linux_amd64/inet.duckdb_extension /tmp/ch/user_files/ext/
```

```sql
CREATE TABLE f (x Int32) ENGINE = DuckDB('fresh.duckdb', 'f');
SELECT duckdbLoadExtension('fresh.duckdb', 'ext/inet.duckdb_extension');   -- 1
SELECT arrayFilter(e -> e.name = 'inet', duckdbExtensions('fresh.duckdb')).loaded;   -- [1]

SELECT duckdbLoadExtension('fresh.duckdb', '../../etc/passwd.duckdb_extension');   -- PATH_ACCESS_DENIED
SELECT duckdbLoadExtension('fresh.duckdb', 'ext/missing.duckdb_extension');        -- BAD_ARGUMENTS
```

An unsigned extension: make a copy of the file with the signature, the last 256 bytes, zeroed. Keep the file name, because DuckDB finds the entry point of the extension by it:

```bash
mkdir -p /tmp/ch/user_files/unsigned
python3 - <<'PY'
d = bytearray(open('/tmp/ch/user_files/ext/inet.duckdb_extension', 'rb').read())
d[-256:] = bytes(256)
open('/tmp/ch/user_files/unsigned/inet.duckdb_extension', 'wb').write(d)
PY
```

```sql
CREATE TABLE u (x Int32) ENGINE = DuckDB('unsigned.duckdb', 'u');
SELECT duckdbLoadExtension('unsigned.duckdb', 'unsigned/inet.duckdb_extension');
-- allow_unsigned_extensions = 0: DUCKDB_ENGINE_ERROR, "its signature is either missing or invalid and unsigned extensions are disabled"
-- allow_unsigned_extensions = 1: 1
```

Set `allow_extension_loading` to `0`, restart, create a table over a fresh database and load `inet` again:

```sql
SELECT duckdbLoadExtension('fresh2.duckdb', 'inet');   -- SUPPORT_IS_DISABLED: set 'duckdb.allow_extension_loading'
SELECT duckdbLoadExtension('fresh2.duckdb', 'json');   -- 1: a built-in extension needs no dlopen
```

### 7. The switches {#test-the-switches}

Set `allow_arbitrary_sql` to `0`, restart the server and run:

```sql
SELECT * FROM duckdb('', 'SELECT 1');   -- SUPPORT_IS_DISABLED
```

Set `allow_extensions` to `0` and restart. The extension functions fail with `SUPPORT_IS_DISABLED`, and the tables keep working, but a query that reads a file, such as one with `read_parquet`, fails because DuckDB has no file system access.

### 8. A query cannot run a second statement {#test-single-statement}

```sql
SELECT * FROM duckdb('app.duckdb', 'SELECT 1 AS a) AS q; CREATE TABLE evil(x INT); SELECT * FROM (SELECT 1 AS a');
-- DUCKDB_ENGINE_ERROR: Cannot prepare multiple statements at once
SELECT count() FROM duckdb('app.duckdb', 'SELECT table_name FROM duckdb_tables() WHERE table_name = ''evil''');   -- 0
```

### 9. Without a server {#without-a-server}

`clickhouse-local` does not validate the configuration sections, which makes it useful for a quick check of a configuration:

```bash
cat > /tmp/duckdb-local.xml <<'XML'
<clickhouse>
    <duckdb>
        <allow_extensions>1</allow_extensions>
        <allowed_extensions>json,parquet</allowed_extensions>
```

## Troubleshooting {#troubleshooting}

| Symptom | Cause |
| --- | --- |
| `error while loading shared libraries: libduckdb.so` | The library is not found: set `LD_LIBRARY_PATH`. |
| The server exits with `UNKNOWN_ELEMENT_IN_CONFIG` for `duckdb` | The binary was built without `ENABLE_DUCKDB`, or is older than the `duckdb` section. |
| `Unknown table function read_parquet` | `read_parquet` is a DuckDB function: call it inside `duckdb('', '...')`. |
| `Unknown format Parquet` | This ClickHouse build has no Parquet format. It is unrelated to DuckDB. |
| `SUPPORT_IS_DISABLED` | `allow_extensions` or `allow_arbitrary_sql` is not set, or the server was not restarted. |
| `SUPPORT_IS_DISABLED` ... `duckdb.allow_extension_loading` | The extension is not built into `libduckdb.so`, and loading native code is not allowed: set `allow_extension_loading`. |
| `signature is either missing or invalid and unsigned extensions are disabled` | The extension is not signed by DuckDB: set `allow_unsigned_extensions` if you trust it. |
| `Failed to download extension ... (HTTP 404)` | The extension does not exist for this DuckDB version and platform in the repository. |
| `ClickHouse does not allow dynamic library loading` | A library other than a DuckDB extension, or a build that is older than `allow_extension_loading`, called `dlopen`. |
| `Cannot access directory ... file system operations are disabled` | The database was opened with `allow_extensions` off, which disables the file system for DuckDB. |
| `Could not set lock on file` | Another process, such as the `duckdb` command line, holds the database file. |

## DuckDB statements {#duckdb-statements}

The `duckdb` table function wraps its argument into a subquery, so it runs the DuckDB statements that DuckDB accepts as a subquery. Every other statement of the [DuckDB statement list](https://duckdb.org/docs/current/sql/statements/overview) is rejected by DuckDB with `DUCKDB_ENGINE_ERROR` before it runs and changes nothing. The test `05412_duckdb_statements` runs every statement of the list.

| Works through `duckdb` | Use the ClickHouse statement of the `DuckDB` engine instead | Not available |
| --- | --- | --- |
| `SELECT`, `FROM`-first `SELECT`, `DESCRIBE`, `SHOW`, `SHOW DATABASES`, `SHOW TABLES`, `SUMMARIZE`, `UNPIVOT`, `PIVOT` with an `IN` list | `CREATE TABLE`, `INSERT`, `SELECT`, `DROP TABLE` (ClickHouse table only), transactions | `UPDATE`, `DELETE`, `MERGE INTO`, `ALTER TABLE`, `ALTER VIEW`, `ATTACH`, `DETACH`, `CALL`, `CHECKPOINT`, `COMMENT ON`, `COPY`, `CREATE INDEX`, `CREATE MACRO`, `CREATE SCHEMA`, `CREATE SECRET`, `CREATE SEQUENCE`, `CREATE TYPE`, `CREATE VIEW`, `EXPORT DATABASE`, `IMPORT DATABASE`, `PREPARE`, `EXECUTE`, `DEALLOCATE`, `PRAGMA`, `SET`, `RESET`, `SET VARIABLE`, `USE`, `VACUUM`, `ANALYZE`, `EXPLAIN`, `BEGIN`, `COMMIT`; `LOAD` and `INSTALL` are available as `duckdbLoadExtension` and `duckdbInstallExtension` |

`PIVOT` without an `IN` list is rejected, because DuckDB expands it into several statements.

## Insert performance {#insert-performance}

`INSERT` into a `DuckDB` table writes the rows with the DuckDB appender in one transaction. The measurements below ran on 1,000,000 rows with one insert thread on this machine:

| Part | Specification |
| --- | --- |
| Machine | Intel Core i5-7600 at 3.5 GHz, 4 cores (4 threads), 40 GB of RAM, macOS 13.7.8 |
| Linux VM | Colima 0.10.3 with the Docker 29.5.2 runtime, `x86_64`, 4 CPUs, 8 GB of RAM, Linux 6.8 |
| Software | ClickHouse 26.11, DuckDB v1.5.6 |
| Disk | The DuckDB file is on the container's file system inside the VM. A synchronous 4 KiB write there takes about 1.8 ms. |

Measured on 2026-11-19:

| Table | Rows per second |
| --- | --- |
| 2 integer columns | about 3,100,000 |
| 9 mixed columns (`Int64`, `String`, `Float64`, `Date`, `DateTime64(6)`, `UUID`, `Decimal`, `Nullable(Int32)`, `Bool`) | about 500,000 |

The size of an insert matters more than any DuckDB setting. Each insert is one DuckDB transaction with a fixed cost, so the rate depends on the rows per insert. These are sequential inserts of `numbers(N)` through the server, in the same run:

| Rows per insert | Inserts per second | Rows per second |
| --- | --- | --- |
| 1 | 66 | 66 |
| 100 | 63 | 6,300 |
| 10,000 | 36 | 361,000 |

### Small inserts {#small-inserts}

Measured on 2026-11-21 on the same machine, a one-row insert took about 14 ms on a server without the full `config.xml`. The time splits into three parts:

| Part | Time per insert |
| --- | --- |
| ClickHouse's own work for the query, measured with a `Null` table | 7.6 ms |
| DuckDB's commit: one `fsync` of its write-ahead log | about 2 ms |
| DuckDB's statements and the engine's setup for each `INSERT` | about 5 ms |

ClickHouse's own work is the same with any table engine. Because of it, an insert of 100 rows took about as long as an insert of one row. Batching is the main remedy.

The sync depends on the disk. On a disk with slow syncs it becomes the larger part, so use storage with a low sync latency for many small transactions. In a direct test of the DuckDB library, a one-row transaction took 3.3 to 4.5 ms with a database file, and 0.9 ms with an in-memory database, which does not sync.

DuckDB has no setting that skips or delays the sync at commit, and `strace` shows exactly one `fsync` per commit. `checkpoint_threshold` (also called `wal_autocheckpoint`) and `immediate_transaction_mode` did not change the one-row rate. A one-row commit adds about 126 bytes to the write-ahead log, so the default threshold of 16 MiB is reached only every 130,000 commits or so. A very small `checkpoint_threshold` made the inserts slower.

The server's full `config.xml`, with its system log tables and a trace-level log file, added about 2 ms to every query: 9.4 ms instead of 7.6 ms. With that configuration, a one-row insert into a `MergeTree` table took about 75 ms, because each insert writes a new part.

### Comparison with the `SQLite` and `PostgreSQL` engines {#comparison-with-sqlite-and-postgresql}

Measured on 2026-11-21 on the machine above, with 1,000,000 rows. Each figure is the median of three alternating rounds.

This build does not include the `SQLite` and `PostgreSQL` engines, so they ran in the official ClickHouse 26.12 build. PostgreSQL 17.11 ran with default settings in a container on the same VM, reached over local TCP. The SQLite file used default settings, with a rollback journal.

| Rows per second | `DuckDB` | `SQLite` | `PostgreSQL` |
| --- | --- | --- | --- |
| Insert, 2 integer columns | **2,800,000** | 1,570,000 | 1,320,000 |
| Insert, 9 mixed columns | **489,000** | 312,000 | 234,000 |
| Engine's own time for the 9-column insert | **1.77 s** | 3.03 s | 4.11 s |
| 1 row per insert | 61 | 56 | **94** |
| 100 rows per insert | 6,320 | 6,010 | **9,350** |
| 10,000 rows per insert | 381,000 | 328,000 | 399,000 |
| Scan, 2 integer columns | 2,270,000 | **3,460,000** | 2,420,000 |
| Scan, 9 columns with `count`, `sum` and `length` | **2,870,000** | 2,510,000 | 1,170,000 |
| Scan, all 9 columns | **906,000** | 791,000 | 614,000 |

The engine's own time is the 9-column insert minus an insert of the same rows into a `Null` table. The official build does ClickHouse's own bulk work faster: 5.9 million rows per second into `Null`, against 3.8 million for this build. The insert rows therefore understate the `DuckDB` engine. The engine's own time removes that difference.

The `DuckDB` figures come from a server with the full `config.xml`. Without it, as for the other two, the one-row rate was 70.

For a one-row insert, the time each engine adds to ClickHouse's own work is shown below. Both servers ran without `config.xml`, and the disk calls were counted with `strace`.

| Per one-row insert | `DuckDB` | `SQLite` | `PostgreSQL` |
| --- | --- | --- | --- |
| Total | 14.3 ms | 17.7 ms | 10.6 ms |
| ClickHouse's own work (`Null` table) | 7.6 ms | 7.8 ms | 7.8 ms |
| Engine and database | 6.7 ms | 9.9 ms | 2.8 ms |
| Disk calls | 1 `fsync` of a growing log file | 4 `fsync`, plus creating and deleting a journal file | 1 write and 1 `fdatasync` in the PostgreSQL server |

- **`PostgreSQL`** has the cheapest commit, even though it runs as a separate server. It syncs its log with `fdatasync` into files that already have their full size, which took 0.7 to 0.9 ms here, and the engine reuses pooled connections.
- **`SQLite`** syncs four times per commit with its default rollback journal.
- **`DuckDB`** syncs once, but with `fsync` on a log file that grows. That also writes the file system's metadata and took 1.8 to 2.2 ms here. The rest of its time is DuckDB's statement work and the engine's setup for each `INSERT`.
- **Scans:** no engine pushes aggregation down, so every row is copied into ClickHouse. PostgreSQL computed the same aggregates by itself about 5 times faster, using parallel workers.
- **Without ClickHouse:** PostgreSQL alone, through `psql`, did 625 one-row inserts per second.

### DuckDB settings and batching {#duckdb-settings-and-batching}

The DuckDB tuning settings `threads`, `ROW_GROUP_SIZE`, `preserve_insertion_order` and `COMPRESS` did not change the insert rate in tests with the DuckDB library (3 to 10 million rows). `threads` made scans of the table faster, from 0.65 s with one thread to 0.13 s with four, and the default already uses all the cores.

Earlier versions ran one `INSERT` statement for each row, which was about 1,000 to 1,400 rows per second. Larger inserts are faster than many small ones, because each insert is a transaction: insert in batches and avoid one-row inserts. `Date`, `DateTime64` and `Decimal` values are cast by DuckDB from text, which costs more than the numeric and string columns.

## Limitations {#limitations}

- Linux only, and `libduckdb.so` is a run-time dependency.
- `WHERE`, `LIMIT` and aggregations are not pushed down into DuckDB for the `DuckDB` engine: the requested columns are read and filtered in ClickHouse. Use the `duckdb` table function to run the filter in DuckDB.
- No `ALTER ... UPDATE`, `ALTER ... DELETE` or `TRUNCATE`. `DROP TABLE` drops the ClickHouse table, not the DuckDB one.
- A loaded extension is native code of the server process. It is not sandboxed, and cannot be unloaded until the database is closed.
- A DuckDB extension must be built for the same DuckDB version and platform as `libduckdb.so`.
- The map of the functions of the built-in extensions is a fixed list. For the other extensions it is recorded when they are loaded, so it is empty for a database where the extension has not been loaded by the server.
